# ループの振り返り

実装ループ（implementer → reviewer → integrator → verifier）は、上流の段階で問題を捕まえるほど安く済む。下流で捕まった、または誰も捕まえられなかった事象は、上流のどこかに欠けがある。その欠けをルール・agent 定義・skill に還元するのがこの手順。

## トリガー

以下のいずれかが起きたタスクで実施する。

- reviewer の差し戻しが上限（2 往復）を超えて打ち切った
- integrator が `CHANGES_REQUESTED` を返した（個別レビューを通った変更が統合で壊れた）
- verifier が `NG` を返した（PR 前の検査をすべて通過した変更が実環境で壊れた）
- hook（`settings.json` に登録した PreToolUse / SubagentStop）がサブエージェントまたは本体の操作をブロックした
- ユーザーがレビュー通過後の成果物に修正を求めた

## 手順

1. 事実を 1 行ずつ書く。どの段階で何が見逃され、どの段階で捕まったか。推測を混ぜない
2. なぜ上流で捕まらなかったかを以下のいずれかに分類する
   - 指示不足: 委譲指示・計画に必要な情報が欠けていた。反映先は `delegation` skill の「指示に含める要素」か planner の定義
   - 判定器不足: 検証コマンドが定義されていなかった、または実行されなかった。反映先はリポジトリの CLAUDE.md / `.claude/rules` の検証定義、または hook
   - 知識不足: リポジトリ固有の規約・前提を知らなかった。反映先はリポジトリの `.claude/rules`（`memory-policy` の書き分けに従う）
   - agent 定義の欠陥: 役割境界・観点・判定ルールに漏れがあった。反映先は `~/.claude/agents/<name>.md`
3. 反映を提案する。差分の形でユーザーに示し、合意なしに CLAUDE.md・agent 定義・skill を変えない。毎セッション読み込まれるファイルへの追加は `memory-policy` の「書く前の判断」を通す
4. 日報の該当タスク見出し配下に記録する（書式は下記）

## 反映の判断

- 同じ分類の事象が 2 回以上出たときに反映を提案する。1 回の失敗で規則を増やさない
- ただし `blocker` 相当（本番影響、データ破壊、機密情報）は 1 回で提案する
- 再発の判定には過去の日報の `ループ:` 行と `### ループの振り返り` を使う。`grep -r "ループ:" ~/Documents/me-vault/daily-reports/` で引ける

## 日報の書式

ループを回したタスクは、結果が正常でも見出し配下の末尾に 1 行置く。

```
ループ: reviewer 差し戻し 1 回 / integrator PASS / verifier OK
```

- reviewer は差し戻し回数。0 回なら `0 回`
- integrator は `PASS` / `CHANGES_REQUESTED` / `省略`（1 タスクまたは直列のとき）
- verifier は `OK` / `NG` / `未反映` / `対象外`（クラスタに反映されない変更のとき）

トリガーに該当した場合は続けて置く。

```
### ループの振り返り
- 事象: reviewer PASS の変更が integrator で CHANGES_REQUESTED。T1 の変数名変更に T2 が追随していなかった
- 分類: 指示不足。T2 の委譲指示に T1 の変更内容を添えていなかった
- 反映: 今回は記録のみ。同じ分類は初回
```

太字は使わない（`daily-report` の書式に従う）。
