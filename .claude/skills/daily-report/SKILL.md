# 日報

## 対象とするタスク

- 記録する価値がある作業を対象とする（成果物が残る、意思決定をした、外部に影響を与えた、複数ターン・ツール実行を伴った）。PR の有無は問わない
- 会話の中で完結する質問への回答や、既知の内容の説明だけなら確認しない
- タスクごとに確認する。1 セッションで複数タスクを終える場合はまとめない。実装ループが何周しても確認は 1 タスクにつき 1 回

## ファイル

- 保存先: `~/Documents/me-vault/daily-reports/YYYYMM/YYYYMMDD.md`（当日の日付。年月のディレクトリ配下に置く）
- 月が変わった初日は当月のディレクトリがまだ存在しないため、先に作成する。直下に置いて月末にまとめて移す運用は廃止した
- 同名ファイルが既に存在する場合は、上書きせず末尾に追記する
- ただし同一タスクの記載が既にある場合は、新たな見出しを立てず該当タスクの見出し配下に内容を統合する

## 見出し・書式

- タスクごとに `## タスク名` を立てる。`## 作業内容` のような総括見出しで括らない
- 同一タスクの追加作業を記録する際は「追記」という見出しを作らず、該当タスクの見出し配下に統合する
- タスクに紐づかない知見・申し送りは、それを得たタスクの見出し配下に `### 申し送り` として置く。独立した `## その他` を作らない
- Markdown の太字記法（`**`）は使用しない
- 実装ループ（implementer → reviewer 以降）を回したタスクは、見出し配下の末尾に `ループ:` 行を 1 行置く。判定が異常だった場合は続けて `### ループの振り返り` を置く。書式はいずれも `loop-retro` skill

## 記載しないもの

- バリデーションコマンド（`kubectl kustomize`、`terraform validate` 等）の実行。結果が異常だった場合のみ記録する
- merge conflict の解消作業そのもの。対応方針に特筆すべき判断があった場合のみ記録する
- 作業途中の不要な差分破棄など、最終成果物に残らないノイズ処理
- 具体的なファイルパス（PR で追えるため）。コンポーネント名・namespace・リソース種別など意味のある単位で言及する

## 記載の焦点

成果・意思決定・特筆すべき判断にフォーカスする。

## 完了手順

日報の記録を承諾された時点で、以下を順に実施する。途中でユーザーに確認を挟まない。

1. 上記のルールに従って日報を記録する
2. 作業用に作成した worktree とブランチを削除する（`git worktree remove <path>` → `git branch -D <branch>`）。epic ブランチを立てていた場合、PR がマージ済みであることを確認してから epic 用の worktree とブランチも削除する
3. ローカルの main ブランチを最新化する（`git checkout main && git pull`）
4. 関連する Jira チケットがあればステータスを完了へ遷移させる（`jira-infra` skill）
