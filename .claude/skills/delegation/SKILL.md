# サブエージェントへの委譲

## 実装を伴うタスクのループ

git 操作はすべて本体が行う。サブエージェントにブランチ・worktree の作成や commit をさせない。

1. `investigator` に委譲し、変更対象と現状を把握する（自明な場合を除き省略しない）
2. `planner` に委譲し、タスク分解と実行順序を得る。ファイル変更を伴うタスクでは常に通す
3. 計画をユーザーと合意する
4. 本体がデフォルトブランチ（`main` 等）から epic ブランチを作成する
5. 本体が epic からタスクごとに worktree を作成し、作業ディレクトリの絶対パスを含めて `implementer` に委譲する。依存のないタスクは並列に回す
6. タスクごとに `reviewer` へレビューを委譲する
7. `CHANGES_REQUESTED` → 指摘全文を添えて 5 に戻す / `PASS` → 8 へ
8. 本体が epic へマージし、worktree とタスクブランチを削除する
9. 全タスク完了後、`integrator` に epic 全体の統合レビューを委譲する
10. `CHANGES_REQUESTED` → 修正タスクとして 5 に戻す / `PASS` → 11 へ
11. 本体が epic を push し、デフォルトブランチ向けの PR を作成する
12. PR がマージされた後、GitOps でクラスタに反映される変更なら `verifier` に動作確認を委譲する

## ブランチと worktree

epic ブランチはタスク全体でひとつ。各タスクの worktree は epic から切り、epic に戻す。マージ先が一意になるため統合の手間が生じない。

```
main
 └── epic/PROJ-123-karpenter          ← 本体が作成、PR のソース
      ├── epic/PROJ-123-karpenter/T1   ← worktree、マージ後に削除
      └── epic/PROJ-123-karpenter/T2
```

配置は `~/Develop/worktrees/<リポジトリ名>/<ブランチ名>`。

```
# epic ブランチと、そのマージ先となる worktree
git worktree add ~/Develop/worktrees/<repo>/epic/<name> -b epic/<name> <default>

# タスクごとの worktree（epic から切る）
git worktree add ~/Develop/worktrees/<repo>/epic/<name>/T1 -b epic/<name>/T1 epic/<name>
```

epic 用の worktree は最後まで残す。マージ先であり、`integrator` の作業ディレクトリになり、PR の push 元になる。

epic 名は Jira キーがあれば `epic/<Jiraキー>-<短い説明>`、なければ `epic/<短い説明>`。

タスクが 1 件しかない場合は epic を作らず、デフォルトブランチから直接タスクブランチを切ってよい。中間ブランチが無駄になるため。

## 分解されたタスクの回し方

- 依存のないタスクは並列に `implementer` へ投げる。依存関係は planner の `実行順序` に従う
- 同じファイルを触るタスクは並列にしない。planner が分解時に同一ファイルの変更をまとめる前提だが、またがっている場合は本体が直列に落とす
- 並列タスクはそれぞれ別 worktree で動かす。同一 worktree への並列実装はしない
- レビューはタスクごとに通す。全タスク完了後にまとめてレビューしない（差分が大きくなると指摘の精度が落ちる）
- 途中のタスクで計画の前提が崩れたら、残りのタスクを実行せず planner に計画を組み直させる

## epic へのマージ

タスクが `PASS` したら本体が epic へマージする。並列実行では先行タスクのマージによって後続タスクの worktree が古くなるため、以下の順で扱う。

1. epic へマージする（`git merge --no-ff`）
2. コンフリクトした場合は、本体で解消せず `implementer` に epic の最新を取り込ませてから再度 `reviewer` を通す。コンフリクト解消は実質的な実装判断であり、レビューを経ずに本体が行わない
3. マージ済みのタスクブランチと worktree を削除する（`git worktree remove` → `git branch -d`）

## 統合レビュー

並列実行では、各 `implementer` は他タスクの変更が入っていない状態のコードを見て作業し、各 `reviewer` も自分の worktree しか見ない。したがって「全タスク PASS だが epic にマージすると壊れる」が起こりうる。T1 が変えた関数シグネチャに T2 が追随していない、といった境界の不整合がこれにあたる。

これを検出するため、全タスクのマージ後に `integrator` へ委譲する。

渡すもの:

- epic ブランチの worktree の絶対パス
- デフォルトブランチ名（差分の起点として使う）
- `planner` の計画全文（要件充足の照合に使う）
- 各タスクの `implementer` 報告と `reviewer` 判定（何が既にレビュー済みかを知らせ、重複指摘を防ぐ）
- 実行してほしい検証コマンド（planner が各タスクの `検証` に挙げたものの和集合）

`integrator` は個別タスクのコード品質を見ない。タスク境界の不整合・計画との照合・統合状態での検証に絞る。個別の観点は `reviewer` が済ませている。

`CHANGES_REQUESTED` の場合は、原因タスクへ巻き戻さず修正タスクとして epic から worktree を切り、`implementer` → `reviewer` を通してから `integrator` に再レビューさせる。マージ済みのため巻き戻しは現実的でない。個別レビューを通った変更が統合で壊れたということなので `loop-retro` の対象。

省略してよい場合:

- タスクが 1 件だけだった場合（境界の不整合が原理的に起きない）
- 全タスクを直列で回した場合（後続タスクが先行タスクの結果を見た上で実装され、その状態で `reviewer` も通っている）

検証手段がないリポジトリでは `integrator` は `PASS` を返さない設計にしてある。その場合は統合状態を確認できていない事実を PR 説明とユーザーへの報告に明記する。

## マージ後の動作確認

`integrator` までは Git 上の検査であり、実クラスタには触れていない。FluxCD / Argo CD による GitOps 構成のリポジトリでは、マージしてもクラスタへの反映には時間差がある。反映後に実物を確認するのが `verifier` の役割。

`integrator`（PR 前・静的検査）と `verifier`（PR 後・実クラスタ）は別フェーズ。混同しない。

委譲するのは、マージによってクラスタの状態が変わる変更に限る。ドキュメントのみ、CI 設定のみといった変更では不要。

渡すもの:

- リポジトリの絶対パス（kubeconfig の相対パスの起点になる）
- クラスタへの接続方法。リポジトリ固有の kubectl skill（`~/.claude/skills/kubectl-<org>/SKILL.md`）があればそのパスを渡す
- 対象環境（dev / prd 等）。推測させない
- マージしたコミット SHA と PR 番号（反映の照合に使う）
- 何が変わったか（変更したリソース、namespace、期待される状態）
- 反映待ちの上限時間（指定しなければ数分を目安に判断させる）

`verifier` はクラスタの状態を変更しない。`flux reconcile` も実行させない。反映は待つものとして扱い、時間内に反映されなければ `未反映` を返す。`prd` では読み取り範囲も最小限に絞らせる。

判定の扱い:

- `OK` → 完了。日報へ
- `NG` → 修正が必要。デフォルトブランチから新たに修正のループを回す（epic は既にマージ済みのため巻き戻さない）。本番影響がある場合はロールバックの要否を先にユーザーへ確認する。PR 前の検査をすべて通過した変更が実環境で壊れたということなので `loop-retro` の対象
- `未反映` → 反映を待って再度 `verifier` を呼ぶ。反映が進まない場合は Flux / Argo CD 側の問題を疑い、`investigator` に原因を調べさせる

`verifier` が `OK` を返すまで「動作確認済み」と報告しない。

## planner への委譲

- `investigator` の報告は要約せず全文を渡す。planner は自分で調査せず、報告を土台に計画を組む前提で書かれている
- ユーザーの依頼も原文で渡す。要約すると意図が落ちる
- 計画が返ったら本体が内容を検証する。丸呑みしない。前提が調査報告と食い違っていないか、依頼の範囲を超えていないかを確認する
- `追加調査が必要な点` があれば、`investigator` に問いを投げてから planner に差し戻すか、本体が答えを補って計画を確定させる
- `決めてほしいこと` は 3 でユーザーに提示する。planner の推奨をそのまま採用せず、本体の判断を添える

## レビューの重大度と判定

| 重大度 | 対象 |
|---|---|
| `blocker` | 動作不良・データ破壊・セキュリティ問題・要件未達 |
| `major` | 実害が出る可能性が高い、または検証が不足 |
| `minor` | 保守性の問題 |

`blocker` か `major` が 1 件以上あれば `CHANGES_REQUESTED`、`minor` のみか指摘なしなら `PASS`。

したがって `PASS` でも指摘が残ることがある。その場合は差し戻さず、指摘を提示して対応するか確認する。

差し戻しは最大 2 往復まで自動で回す。超えても `CHANGES_REQUESTED` が残る場合は打ち切り、残った指摘と対立点を整理してユーザーに判断を仰ぐ。この打ち切りは `loop-retro` の対象。

## 指示に含める要素

サブエージェントは会話の文脈を持たない。以下を必ず含める。

- 作業ディレクトリの絶対パス
- 対象ディレクトリと変更すべきファイルの範囲
- 達成すべきこと（ユーザーの意図まで言語化する。指示の丸写しにしない）
- 守るべき制約（既存パターン、触ってはいけない箇所、ブランチ名）
- 実行してほしい検証（テスト、lint、`terraform validate`、`kubectl kustomize` 等）

計画がある場合、該当タスクの `対象` / `内容` / `制約` / `検証` をそのまま使える。ただし作業ディレクトリの絶対パスは本体が補う（planner は worktree を知らない）。他タスクとの関係で知っておくべき文脈があれば添える。

## 差し戻しとレビュー依頼

- 差し戻し時はレビュー指摘を要約せず、指摘 ID を保ったまま全文を渡す
- `reviewer` には実装指示の内容と `implementer` の報告全文を併せて渡す。レビュアーが「何を達成すべきだったか」を知らないと要件との一致を検査できない

## investigator への委譲

- 依頼は具体的な問いの形にする。「調べて」ではなく「何を答えてほしいか」を書く
- 互いに依存しない調査は 1 メッセージで複数同時に投げ、並列実行させる
- 報告はそのまま貼らない。ユーザーに問われたことへの答えとして再構成する

## ループの振り返り

上記で `loop-retro` の対象と書いた事象が起きたら、タスク完了後に `loop-retro` skill を読み、なぜ上流の段階で捕まらなかったかを分類してルール・agent 定義・skill への反映を提案する。ループを回したタスクは、結果が正常でも日報に `ループ:` 行を残す（書式は `loop-retro`）。反映の要否は同じ分類の再発で判断するため、正常時の記録も省略しない。

## ユーザーへの還元

- `implementer` の報告に `questions` / `concerns` があれば本体がユーザーに提示する。仮定を置いたまま進んだ箇所は commit 前に確認する
- ユーザーから成果物への指摘があった場合も原則 `implementer` に差し戻して `reviewer` を通す（typo 級の軽微な指摘は本体で直してよい）
- レビューを通った変更が「何をどう変えたか」は本体が把握しておく（差分の全文ではなく、変更ファイルと意図のレベル）。PR 説明・日報・後続の修正指示の質がそこに依存する
